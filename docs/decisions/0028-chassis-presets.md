# 0028. Выбираемые корпуса: три пресета, carry и jump у каждого

- Статус: Accepted
- Дата: 2026-10-29
- Дополняет: [0004](0004-visual-prefabs-and-scene-actors.md).
- Заменяет в части клипов: [0013](0013-jump-menu-views-motorcycle.md) (прыжок только
  у `R1`), [0018](0018-menu-showcase-carousel-and-ice-road.md) (`CarryWalk` только у `R18`).

> **Дополнение 2026-10-29.** Кроме `CarryWalk` трём корпусам нужен **`CarryIdle`** —
  стойка с грузом. Клипа в паке нет: `robot_lib._make_carry_idle` собирает его из
  позы `walk_carry_loop` (30 кадров, петля). Флаг `--carry-idle`; постпроцессор раздаёт
  клип тем же трём id, `R18` остаётся только с `CarryWalk`. Собрано и импортировано.

## Контекст

Сейчас игрок — всегда `R1_PolarMechanic`: сцена `Game` держит его визуал, Animator,
кость головы и `SkinnedMeshRenderer` зашитыми. Прыжковые клипы есть только у `R1`
(ADR 0013), `CarryWalk` — только у `R18` (ADR 0018), и EditMode-тесты это закрепляют
(`PlayerRobot_HasJumpClipsAndStates`, `CarrierRobot_HasCarryWalkAndOthersDoNot`).

Сюжет требует выбора из трёх корпусов до старта, а переноска аккумуляторов — часть
первого квеста. Значит выбранный корпус обязан и прыгать, и носить. Модульная сборка
из частей сейчас невозможна: каждый FBX — один слитый меш, части существуют только
в Blender-скрипте и не экспортируются отдельно.

## Решение

1. **Три пресета — три цельных визуальных префаба.** `R1_PolarMechanic`,
   `R10_Pipewright`, `R15_Courier`. Профиль — ScriptableObject `RobotProfile`:

   ```
   RobotProfile
     id             строка (совпадает с именем префаба без суффикса)
     displayName    латиница для UI
     role           короткая строка для карточки
     description    абзац для карточки
     visualPrefab   R*_Model
     walk / sprint / carry / jump   множители > 0
   ```

   `CharacterCatalog` — SO со списком профилей и `defaultId`. Точные значения
   множителей — данные, а не код (GDD, «Герой»).

2. **`CharacterSelection` — статика только для передачи выбора между сценами.**
   Хранит `SelectedId`, пишет в `PlayerPrefs` (`FrostSpace.Character`), читает при
   старте, сбрасывается в
   `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` — domain reload выключен.
   Это тот же приём, что у `GameSettings`.

3. **Клипы ношения и прыжка получают все три корпуса.** `RobotAssetPostprocessor`
   назначает `CarryClips` и `JumpClips` списку из трёх id вместо одного. `R18_Forge`
   сохраняет `CarryWalk` (он носильщик в меню), но прыжка у него по-прежнему нет.
   Остальные 16 роботов не меняются.

4. **Контроллеры получают состояния.** У `R1`, `R10`, `R15` появляются `Carrying` /
   `CarryWalk` и `JumpStart` / `JumpLoop` / `JumpLand` с теми же параметрами, что у
   `R1` сейчас. `RobotLocomotion` не меняет логику: он уже умеет прыжок и умеет
   включать клип переноски по флагу.

5. **Скорость `CarryWalk` измеряется, а не подбирается.** Для каждого из трёх FBX
   прогоняется `measure_locomotion.py`; полученная скорость клипа попадает в
   `_carryClipSpeed` (аналог `_walkClipSpeed`) и в контроллер. Иначе ноги будут
   скользить при переноске.

6. **Профиль применяется один раз при спавне.** `PlayerVisualBinder` получает
   `RobotProfile`, ставит визуальный префаб ребёнком актёра и вызывает
   `RobotLocomotion.ApplyProfile(walk, sprint, carry, jump)`. Множители умножают
   базовые поля, а не заменяют их: базовые значения остаются в сцене и видны дизайнеру.

7. **Перепривязка визуала — публичные методы, а не поиск по сцене.**
   `PlayerCameraRig`, `PlayerLocalView`, `PlayerSilhouette`, `PlayerAimPose` получают
   `Rebind(Animator animator, Transform head)`. Порядок: визуал создан → `Rebind`
   вызван → камера и HUD включаются. Без этого смена префаба оставила бы камеру на
   старом Animator.

8. **Модульность — отдельный этап.** Кнопка `CREATE YOUR OWN` на экране выбора видна,
   но неактивна. Части (голова/тело/руки/ноги) не экспортируются, пока Blender-пайплайн
   не научится отдавать их отдельными мешами на общем риге с манифестом слотов.

## Последствия

- EditMode-тесты меняются: «у `R1`, `R10`, `R15` есть carry и jump; у `R18` — только
  carry; у остальных — ничего». Старые утверждения об эксклюзивности удаляются, иначе
  тесты и пайплайн разойдутся.
- Три FBX пересобираются с `--carry --jump`; импорт становится дороже на шесть клипов
  на корпус — это осознанная плата за выбор героя.
- Появляется первая статика выбора персонажа; её сброс обязателен при выключенном
  domain reload.
- Выбор героя не влияет на внешность NPC: они остаются на своих префабах.
- `PlayerVisualBinder` — единственное место, где визуал игрока подменяется; сцена
  `Game` не переделывается, пока не будет выведена из потока.

## Альтернативы

- **Клипы у всех 20 роботов.** Отклонено: шесть лишних клипов × 20 FBX раздувают
  импорт и контроллеры, а прыгают и носят только игрок и носильщик меню.
- **Переноска без клипа, процедурной позой.** Отклонено: владелец просил анимацию
  ношения; процедурная поза не даёт шага с грузом.
- **Сборка визуала из частей уже сейчас.** Отклонено: части не экспортируются,
  манифеста слотов нет; это самостоятельный этап Blender-пайплайна.
- **Отдельный префаб игрока на каждый корпус со своей логикой.** Отклонено: логика
  живёт на сценовом актёре (ADR 0004), дублировать `CharacterController` и
  `RobotLocomotion` в префабах нельзя.
