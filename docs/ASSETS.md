# Контракт ассетов Blender → Unity

Здесь только правила перехода ассетов в Unity. Как запускать Blender и его грабли —
`BLENDER.md`. Структура папок — `PROJECT_MAP.md`.

## Единицы и оси

| Понятие | Blender | Unity |
|---|---|---|
| Единица | 1 unit = 1 м (при `unit_settings.scale_length = 1.0`) | 1 unit = 1 м |
| Вверх | +Z | +Y |
| Вперёд | −Y | +Z |
| Вбок | +X | +X |

FBX-экспортёр конвертирует оси. Не «поправляй» поворот объекта на глаз: проверяй
габарит и ориентацию после импорта в Unity.

**Отражение по X — отдельная ловушка.** `bake_space_transform=True` даёт левостороннюю
конверсию осей: модель приезжает зеркальной, при этом габарит совпадает, и bbox-проверка
её не ловит. Поэтому статика экспортируется только через `export_static` (зеркало X +
переворот граней), а ориентация проверяется по **асимметричному признаку** (крыльцо,
труба, занос рельефа). Причина и числа — ADR 0007.

## FBX: статика

Для статической геометрии:

- `bake_space_transform=True` — обязательно. Без него экспортёр объявляет файл Y-up, а
  вершины пишет в осях Blender; объект приезжает «на ребро».
- зеркало X (`export_static(..., mirror_x=True)`) — обязательно для статики: компенсирует
  отражение от `bake_space_transform` (ADR 0007).
- `apply_unit_scale=True`, `global_scale=1.0` — единицы не должны меняться «по пути».
- `mesh_smooth_type="FACE"` — flat shading для low-poly.
- `use_selection=True` — в файл попадает только выбранное, а не вся сцена.

Проверка — не глазами в Blender, а габаритом после импорта: сравни `obj.dimensions` до
экспорта и мировой bbox после обратного импорта. `Tools/Blender/selftest.py` делает это
автоматически с допуском 5 мм.

Всё это (сборка → проверки → превью) запускается одной командой через
`python Tools/Blender/build_all.py --asset <id> --check` (ADR 0017). Только такой прогон
считается сделанной работой по ассету; разовая правка в GUI-Blender — черновик.

## FBX: скелет и анимация

- Экспортируй только меш и арматуру (`use_selection=True`), иначе в файл попадут чужие
  объекты сцены.
- Без NLA экспортёр перебирает **все** действия файла: в один FBX могут попасть клипы
  чужих моделей. Если клипов несколько — используй NLA-полосы этой арматуры.
- Ключи ставь на все деформирующие кости во всех клипах. Иначе Unity «протекает» позами
  между клипами: кость, у которой нет ключа в текущем клипе, сохраняет значение из
  предыдущего.
- Проверяй ≤4 влияния веса на вершину — это требование Unity-скина.
- После экспорта проверь имена клипов и число каналов (например, разбором GLB), а не
  только факт создания файла.

## Роботы FrostSpace: FBX с клипами

Двадцать роботов собраны скриптом, а не импортированы из `AssetSource/`:

- Генерация: `Tools/Blender/build_robots.py` (ядро `robot_lib.py`, дизайны
  `robot_designs.py`), выход — `Assets/_Project/Content/Models/Robots/R*.fbx`.
- Имена не меняются. Принятая партия: `R1_PolarMechanic.fbx`, `R2_Furnace.fbx`,
  `R3_Scout.fbx`, `R4_Hauler.fbx`, `R5_Ranger.fbx`. Вторая партия (принята
  2026-10-18, все 15 остаются):
  `R6_Smelter`, `R7_Drifter`, `R8_Bulwark`, `R9_Tinker`, `R10_Pipewright`,
  `R11_Snowplow`, `R12_Beacon`, `R13_Prospector`, `R14_Medic`, `R15_Courier`,
  `R16_Warden`, `R17_Hermit`, `R18_Forge`, `R19_Tide`, `R20_Cogsmith`.
- В каждом FBX три клипа: `walk_loop`, `idle_loop`, `sprint_loop`; `RobotAssetPostprocessor`
  переименовывает их в `Walk`, `Idle`, `Sprint`, включает loop и конвертирует цвет
  материалов из sRGB в линейный (иначе роботы выглядят выбеленными). Из палитры цвет и
  roughness переносятся (`_Smoothness` = 1 − roughness, сверено по всем материалам),
  а `metallic` — нет: `_Metallic` = 0 у всех роботов.
- **Прыжок есть только у `R1_PolarMechanic`**: сборка с флагом
  `-- --jump` добавляет клипы `jump_start`/`jump_loop`/`jump_land`, постпроцессор даёт
  им имена `JumpStart`/`JumpLoop`/`JumpLand` (loop только у `JumpLoop`). Остальные
  роботы собираются без флага — шесть лишних клипов на модель не нужны NPC (ADR 0013).
- Клипы **in-place** (корневое смещение обнулено). Root Motion выключен, движение в игре —
  kinematic; согласование стопы и корпуса — через `Animator.speed` (ADR 0004).
- Скорость стопы в контакте, м/с: Blender `measure_locomotion.py` даёт walk 0.93 /
  sprint 8.92; разовый замер в Unity — 0.91 / 8.92. Источник истины для сцены — замер
  Unity: значения зафиксированы в скрытых полях `_walkClipSpeed`/`_sprintClipSpeed`
  компонента `RobotLocomotion`. Инструмента для повторного замера в проекте нет.
- Визуальные префабы `R*_Model.prefab` — варианты FBX-модели (`PrefabAssetType.Variant`)
  с `Animator` и `R*.controller`; без `CharacterController`, ввода и логики.

## Робо-животные FrostSpace: FBX с клипами

13 животных собраны скриптом на ригах Quaternius из `AssetSource/` (в `ThirdParty/` пак не
импортируется): 12 видов — гибрид «исходная оболочка + робо-броня», паук собран целиком
процедурно. Причина и альтернативы — ADR 0009; источник, лицензия и что именно взято —
`Content/Models/RobotAnimals/SOURCE.md`.

- Генерация: `Tools/Blender/build_animals.py` (ядро `animal_lib.py`, дизайн
  `animal_designs.py`), выход — `Content/Models/RobotAnimals/<Species>/RA_<Species>.fbx`,
  регистр — `Tools/Blender/animal_manifest.json`. Сборка по именам: `-- Wolf Cow`,
  без аргументов — все 13.
- В FBX два клипа — `Idle` и `Move` (take `idle_loop`/`move_loop`); `AnimalAssetPostprocessor`
  даёт имена, включает loop и конвертирует цвет материалов sRGB→linear. Длина клипа у
  каждого вида своя, поэтому границы кадров берутся из FBX, а не из констант в коде.
- **Стоячий хвост клипа срезается.** У фермерской пачки Quaternius `Walk` вдвое длиннее
  цикла: после шагов идут реальные ключи стояния (линейный дрейф ~0.0002 на кадр), в игре
  это читается как «шаг — пауза — шаг». `animal_lib._static_tail` режет такой хвост, но
  только если поза на срезе замыкает петлю (остаток ≤ 5 % амплитуды). Длины после среза
  (кадры `Idle`/`Move`): Cow 149/40, Horse и Zebra 149/32, Llama и Sheep 149/26,
  Pig и Pug 149/35; Wolf 39/39, Cat 39/40, Dog 39/39, Eagle 39/29, Piranha 38/38,
  Spider 60/30 — как в источнике (Spider — 30 fps, остальные 24).
- Клипы **in-place**: `bake_root_motion` создаёт кость `Root` и ключует её в нуле, поэтому
  ход за цикл равен нулю, а актёра двигает `NpcController` (ADR 0022). Раньше ход
  запекался в `Root` (`clip_speed × длительность`), но `applyRootMotion` в Unity выключен:
  модель уезжала вперёд на длину шага и щёлкала назад на стыке цикла. Чекер
  `check_animal_clips.py` проверяет именно in-place (ход ≤ 0.02 единицы файла), а скорость
  стопы в манифесте — та, с которой клип играет на месте.
- Масштаб нормируется по метрике манифеста: `height` (десять видов), `width` (Eagle —
  размах крыльев), `length` (Piranha — длина). `unity_scale` в манифесте — ориентир для
  Blender, а не масштаб префаба: фактический масштаб живёт на префабе и проверяется тестом.
- Ориентация: конвенция «вперёд» у паков разная (+X / −Y / +Y); к +Z модель приводится в
  Blender, а итоговое рыскание зашито в префаб-вариант — 0° у десяти видов, 90° у
  Wolf/Cat/Dog, 180° у Eagle. Сценовые актёры дублируют его явным оверрайдом, чтобы правка
  префаба не развернула животное.
- Визуальные префабы `RA_<Species>_Model.prefab` — варианты FBX-модели с `Animator` и
  `RA_<Species>.controller`; без `CharacterController`, `NpcController` и
  `AirPatrolController`, без тега.
- **Проверка артефакта:** `check_animal_clips.py` (`build_all.py --asset animals --check`)
  сверяет готовый FBX с манифестом: длины `idle_loop`/`move_loop`, наличие весов у всех
  вершин, скорость стопы в контакте, наклон подошвы в стойке (≤ 5°), жёсткую привязку
  брони стопы к косточке стопы (вес ≥ 0.99) и ход `Root` против `clip_speed × длительность` (±10 %).
  Скорость замеряется относительно `Root`, поэтому расхождение с `clip_speed_source` означает,
  что клип или масштаб изменились, а манифест (а с ним и `Animator.speed` в сцене) — нет.
- **Стойка определяется уровнем сустава.** `animal_lib.stance_weights` берёт медиану
  высоты сустава стопы за клип, а не минимум: в переносе стопа проносится ниже своего
  уровня, и минимум уехал бы на замах. Кадры у входа в стойку/выхода из неё получают
  вес 0.5 — там стопа перекатывается. Этим же определением пользуется сборка
  (`flatten_feet`) и чекер: доворот идёт вокруг сустава, поэтому набор кадров не
  разъезжается между сборкой и проверкой.
- `min Z` меша проверяется только у наземных: у летающих и плавающих пивот в центре
  тела — норма, минимум печатается справочно.

## Ездовые ходуны FrostSpace: FBX с клипами

Четыре двуногих `Mech_*` из `AssetSource/Ultimate Space Kit - March 2023-…zip` стали
ездовыми: наш корпус построен скриптом на их ригах, а клипы печёт `author_gait`
(паковые как есть не годятся). Пак в `ThirdParty/` не импортируется. Пятый,
`Enemy_Large` (`ME_BruteWalker`), удалён вместе с человеческой веткой: его шаг и
седло на спине в новый механический шаг не вписывались. Причина и альтернативы — ADR 0024.

- Генерация: `Tools/Blender/build_mechs.py` (ядро `mech_lib.py`, дизайн `mech_designs.py`),
  выход — `Content/Models/Mechs/ME_<Unit>Walker.fbx`, регистр — `Tools/Blender/mech_manifest.json`.
  Сборка по имени: `-- PandaWalker`; без аргументов собирается вся партия (сейчас
  один ходун).
- В FBX три клипа: take `idle_loop`/`walk_loop`/`run_loop`, `MechAssetPostprocessor` даёт
  имена `Idle`/`Walk`/`Run`, включает loop и конвертирует цвет материалов sRGB→linear.
  Границы кадров берутся из FBX: покой 100 кадров, шаг 34/28/36/38, бег 22/20/22/22
  (30 fps) — константы в коде устарели бы на первой пересборке.
- Клипы **in-place**: `flatten_root` снимает только горизонтальную часть хода корня
  (вертикальный боб остаётся — он и есть вес походки), а считает её в мировых осях:
  у корневой кости `Body` локальные X/Y — это «вперёд» и «вверх». Чекер
  `check_mech_clips.py` требует ход ≤ 0.02, проверяет, что **объём кабины пуст**,
  и что **стопа не отрывается от голени** (в покое ≤ 0.05 м, в шаге и беге ≤ 0.60 м:
  стопа пака — отдельная кость без родителя, на замахе она штатно уходит вперёд).
- **Походка печётся заново** (`author_gait`, `GAIT_STYLES` в `mech_lib.py`): сначала
  `raise_body` поднимает таз (нога становится длиннее), `straighten_stance` правит rest —
  колено **назад** (обратноколенная стойка шагохода), подошва на `z=0`, — затем каждый
  клип собирается с нуля: **перекат подошвы** с пятки через всю плиту на носок,
  двухзвенный IK бедро–голень, высота таза от геометрии опорных ног плюс боб, крен,
  наклон, доворот таза и контр-доворот груди. Профиль один (`waddle`) и он общий
  для шагоходов: шаг 1.51 м/с, бег 4.08 м/с.
  Длина шага ограничена геометрией, а не вкусом: вынос упирается в вылет ноги, и
  зажатая цель = съехавшая подошва (ADR 0024).
- **Нога — механизм, а не коробка** (`mech_designs._legs`): тазовый узел шире бедра,
  ось колена шире и бедра, и голени (сустав читается в силуэте), голень уже всех,
  на ступне — плоская опорная плита на `z=0`, пятка, носок и привод голеностопа.
  Подошва катится с пятки на носок — по этому перекату шаг и читается.
- **Головы нет ни у одного ходуна:** над креслом стоял лишний сенсорный ящик, владелец
  попросил убрать (ADR 0024). Человеческий риг `Enemy_Large` и его ветка дизайна
  (седло на спине, руки) удалены из `mech_lib`/`mech_designs`.
- Скорость земли в клипе (`clip_speed` в манифесте) замеряется по ходу стопы в стойке,
  как у животных, и она же пишется в `walk_speed`/`run_speed`: `Mech` делит на неё
  фактическую скорость, поэтому `Animator.speed` держится 1.00 без подкрутки
  (зажим 0,55…1,35 остаётся страховкой).
- **Кабина:** у всех четырёх кресло в проёме груди (`COCKPIT` + сдвиг `cockpit_offset`
  под рост наездника). Числа посадки — в манифесте: `seat`, `seat_point`, `grips`
  (полуширина рукояток), `grip` (вынос и высота), `foot`, `foot_half` (полуширина
  подножек — 0,19).
- Префабы `ME_*_Model.prefab` — **не «только визуал»**: у ходуна модель, `Animator`,
  `CharacterController`, `Mech`, `ScanTarget` (`WALKER`) и `RiderCockpit` живут на одном
  корне (исключение из ADR 0004, объяснено в ADR 0024). Дочерние `Seat` (с `MechSeat`,
  едет за костью `Chest`/`Torso`), `Seat Point`, `Grip L/R`, `Foot L/R`, `ExitPoint`.
- **Проверка артефакта:** `check_mech_clips.py` (`build_all.py --asset mechs --check`)
  сверяет длины клипов, отсутствие вершин без веса, in-place, пустую кабину и скорость
  земли; `MechVisualPrefabTests` сверяет префабы с манифестом (якоря, капсула, скорости,
  клипы, состояния). Префабы по манифесту раскладывает `MechPrefabUpdater`
  (меню `FrostSpace/Ходуны/Обновить префабы из манифеста`), а не разовый сниппет.

## Уровень FrostSpace: статика

Уровень собран скриптом, как и роботы; исходники — в `Tools/Blender/`, готовое — в Unity:

- Генерация: `Tools/Blender/build_level.py` (ядро `level_lib.py`, детали `level_parts.py`,
  раскладка `level_layout.py`), выход — 19 FBX в
  `Assets/_Project/Content/Models/Level/`: рельеф, дом (стены/крыша/снег/труба/крыльцо/
  окна/дверь/пол/фундамент), интерьер (печь, койка, верстак, табуреты, полка, лампа,
  вязанка, ящик), деревья, пропы, забор.
- Имена файлов не меняются: сцена и постпроцессор ссылаются на них.
- `LevelAssetPostprocessor` ставит плоские нормали, конвертирует цвета sRGB→linear и
  собирает палитру `Level_*` в `Content/Materials/Level/` (тот же приём, что у роботов).
- Все части — отдельные FBX; сборка дома в сцене — вручную (ADR 0005), оси и габариты
  проверены после импорта (ADR 0007).
- Коллайдеры: рельеф — `MeshCollider`, у частей дома и пропов — конвексные/меш-коллайдеры;
  геометрия без коллайдера (мелкие пропы, снежная плита крыши) не участвует в скрытии
  перекрытий (ADR 0006).
- Превью — AssetSource/Previews/Level/; в Assets/ скриншотов и .blend нет.
- Assets/TextMesh Pro/ — ресурсы TextMeshPro, **не трогать**: Resources/TMP Settings.asset
  задаёт defaultFontAsset, который используют BootScreen, PlayerHud и SceneController
  через TMP_Settings.defaultFontAsset. Меню, пауза, журнал, диалоги и трекер квеста
  берут кириллический `Content/Fonts/LiberationSans Cyrillic SDF.asset`. Шейдеры в
  этой папке — легаси TMP 3.x; в проекте используется только TMP_SDF-Mobile.shader,
  остальные удалены 2026-10-22 как неиспользуемые (TMP 5.x внутри com.unity.ugui 2.6.0).
- Ховербайк — отдельный FBX того же пайплайна: `Tools/Blender/build_hoverbike.py`
  (дизайн — `hoverbike_parts.py`) → `Content/Models/Level/Hoverbike.fbx` (3 196 тр.,
  габарит после импорта 1.12 × 2.47 × 0.83 м). Префаб `Prefabs/Ride/Hoverbike_Model`
  (корпус, `Visual`, `Cushion`) собирается меню `FrostSpace → Ride`; подушка и игровые
  компоненты — на корне префаба, не в FBX (ADR 0012). Якоря посадки `Seat`,
  `Seat Point`, `Grip L/R`, `Foot L/R` — **под `Visual`**: модель качается, наездник
  обязан качаться вместе с ней. Различия посадки задаёт `RiderCockpit` на корне
  (наклон, шея, `KneeOut`, `Seat Point`), а не ветки по типу байка. Подушка — Quad
  под днищем, шейдер `Content/VFX/Shaders/HoverCushion.shader`: два источника вдоль
  днища, скорость их раздвигает, руль изгибает; `_Aspect` переводит UV в пропорции
  вытянутого днища.
- Мотоцикл — там же: `Tools/Blender/build_motorcycle.py` (дизайн
  `motorcycle_parts.py`) → `Content/Models/Level/Motorcycle.fbx` (2 624 тр., габарит
  0.76 × 1.13 × 2.55 м). В FBX три узла: `MotorcycleBody` и два колеса
  `MotorcycleWheelF` / `MotorcycleWheelR`, у каждого **pivot в оси** — меш колеса
  центрирован в нуле, `localPosition` задаёт ось; иначе вращение уводит колесо по кругу.
  Префаб `Prefabs/Ride/Motorcycle_Model` добавляет `CharacterController`, `Motorcycle`,
  `MotorcycleRideVisual`, точки `Seat`/`ExitPoint`, фару, стоп-сигнал и частицы; в сцене
  `Game` он стоит рядом с ховербайком (ADR 0013). **`Seat` — дочерний объект `Visual`**
  (как и у ховербайка): модель качается и кренится скриптом, и наездник должен ехать
  вместе с ней, а не висеть на неподвижном корне.
- Обломки и занос для открытого вида меню — `Tools/Blender/build_wreck_parts.py`
  (`MenuWreckWing` / `MenuWreckFin` / `MenuWreckEngine`) и `build_menu_open.py`
  (`MenuDrift`); палитра та же `Level_*`, в сцену ставятся как обычные пропы.

Всего на карту **791 758 трис** (прогон 2026-11-03), из них террейн 387 200
(121 × 3200), остальное — путь, дороги со столбиками, двор и лес клеток. В памяти при радиусе
резидентности 1 живёт 9 клеток террейна — 28 800
трис, и только те из девяти, через которые проходит линия, несут путь.

- **Один объект — один FBX, чанк — префаб из них.** Файла-чанка `WorldCell_*.fbx`
  нет. Часть носит клетку в имени (`_<i>_<j>`), по нему `Tools/Unity/sync_cell_prefabs.cs`
  собирает и обновляет префаб (ADR 0039). В клетке депо 16 частей: девять — двор
  вместе с лесом (`DepotYard_`, `DepotApron_`, `DepotPlatform_`, `DepotRamp_`,
  `DepotCanopy_`, `DepotHangar_`, `DepotShed_`, `DepotCrane_`, `DepotGrove_`),
  остальное — земля, путь, шпалы, дороги от ворот и к посёлку со столбиками,
  путевые знаки и боковой путь; в клетке станции 20, в чистой пустоши 1. Переехать дорогу, лес или
  настил значит взять один файл, а не пересобирать чанк.
- **Один источник высот.** Вершины берутся из `world_layout.world_height`, и
  сборка сверяет **каждую** вершину с этим полем в допуске 1 см. Клетка, легшая
  «примерно на свой рельеф», — это дыба на дороге и провалившийся робот.
- **Стык проверяется числом.** `_edge_check()` собирает углы всех квадов и
  требует одну высоту в каждой общей точке: прогон даёт **192 721 общий узел, все
  с одной высотой**. Картинкой это не доказывается — Workbench без нужного света
  и с дефолтным `clip_end` 100 м показывает однотонное поле.
- **Рельеф уступает коридору, и это тоже число.** `_corridor_check()` требует,
  чтобы узел решётки на плоском дне выемки лежал ровно на транспортном столе:
  625 узлов совпали, ещё 232 пропущены как лежащие под полом тёплого узла (там
  хозяин — двор, и это другой порядок слоёв).
- **Шаг решётки 15 м выбран поперёк главной геометрии, а не «для красоты»:**
  коридор пути с косогорами 22 м требует хотя бы три узла на поперечное
  сечение. При шаге 30 м в выемку попадал один узел, поверхность соединяла его
  с соседями прямыми палками, и разрез превращался в пологу яму 60 м, в которой
  борта тела пути тонут. Расширение коридора при старом шаге картинку не спасло
  — проверено пробами.
- **Физика.** `MeshCollider` на том же мешу террейна и на метле пути с дорогой;
  шпалы, знаки и мелкие пропы коллайдера не имеют. В кадре живёт 9 клеток,
  значит и активных коллайдеров девять, а не сто двадцать.
- **Префаб, а не сцена.** Клетка открывается в Prefab Mode как самостоятельный
  кусок — это и был смысл выбора (ADR 0036 п.2). Индекс клетки лежит в компоненте

  как депо стало обычным чанком клетки (−2,−2), `DEPOT_GROUND` и `depot_cover`

## Unity: импорт FBX

| Параметр | Значение |
|---|---|
| Scale Factor | 1 (если модель построена в метрах) |
| Forward / Up | +Z / +Y |
| Read/Write | выключено, если `Mesh` не нужен в рантайме |
| Optimize Mesh | включено |
| Import Normals / Tangents | включено, если есть текстуры |
| Compression | Off для героев, Medium для окружения |

**Компенсация масштаба на корне.** Импортёр может положить на корень префаба
компенсацию единиц (в нашем selftest на Blender 5.2.2 локальный меш приехал в
сантиметрах, а на корне появился `scale = 0.01` и поворот 90°). Не затирай её
присваиванием:

```csharp
// правильно: умножить на нужный масштаб
root.localScale = Vector3.Scale(root.localScale, Vector3.one * scale);

// неправильно: компенсация импортёра потеряна, объект станет в 100 раз больше
root.localScale = Vector3.one * scale;
```

Проверяй итоговый мировой габарит, а не локальный масштаб.

## Материалы и цвет

- Проект живёт в **Linear** color space. Цвета из макета/палитры задаются в sRGB и
  конвертируются в C#; иначе картинка молча темнеет (без ошибок и предупреждений).
- В URP текстура назначается так:

```csharp
material.SetTexture("_BaseMap", texture);
```

`material.mainTexture` в URP — молчаливый no-op: свойство есть, но рендер его не читает.

- Материалы переиспользуй. Вариации цвета — через `MaterialPropertyBlock`, а не новый
  материал на каждый объект: иначе ломается батчинг.
- `ReadPixels` в `Texture2D` с флагом `linear: false` возвращает **линейные** значения, а
  `EncodeToPNG` пишет sRGB. Если снимать кадр в `RenderTexture` с
  `RenderTextureReadWrite.sRGB`, PNG получается таким же, как видит игрок.
- **Скриншот `manage_camera` — sRGB, а не линейный** (перепроверено 2026-10-18). Кадр,
  снятый инструментом с той же точки, что и `Main Camera`, совпал с sRGB-рендером в
  `RenderTexture` по распределению (среднее/медиана/перцентили) — файл можно сравнивать с
  палитрой напрямую. Прежняя запись «в файле линейные значения» относилась к другому пути
  съёмки и к `manage_camera` **не применяется**. Симптом ошибки: если перекодировать
  такой PNG «из linear в sRGB» ещё раз, картинка светлеет и теряет насыщенность —
  диагностика начинает врать в сторону «всё блёклое».
- Камера, созданная кодом, не получает `UniversalAdditionalCameraData` автоматически.
  Без него постобработка (например, виньетка) молча не работает. Добавляй компонент
  явно, если настраиваешь URP-эффекты из кода.

## Сторонние паки

| Уровень | Где | Правило |
|---|---|---|
| Сырые архивы | `AssetSource/` (вне git и вне Unity) | не коммитить, не импортировать целиком |
| Импорт | `Assets/ThirdParty/<Pack>/` | только нужные модели, текстуры, материалы |

- Один пак — одна папка. Внутри — `Models/`, `Textures/`, `Materials/` по необходимости.
- В папке пака — `SOURCE.md`: откуда скачано, лицензия, дата, что именно взято.
- Имена файлов — `PascalCase`, без пробелов и кириллицы.
- Скачивание должно быть воспроизводимым: если пак нельзя восстановить по `SOURCE.md`,
  он считается потерянным.

В `AssetSource/` сейчас лежат CC0-паки Quaternius (природа, постройки, интерьер,
персонажи, животные, еда, мебель, RPG-предметы) и архив Ultimate Modular Men. Источник
Ultimate Modular Men в проекте не зафиксирован — при импорте добавь `SOURCE.md` с
подтверждённым источником и лицензией.

### Quaternius: превью в Blender

У части моделей Quaternius материал имеет `Alpha = 0` при режиме `HASHED`: в Blender
превью выглядит пустым. Лечится принудительной непрозрачностью на время превью. **В
Unity это не проблема** — не переноси этот workaround в игровые материалы.

## Имена и папки

- Папки — `PascalCase`; файлы ассетов — `PascalCase`, без пробелов.
- Модели — `Assets/_Project/Content/Models/`, материалы — `Materials/`, префабы —
  `Prefabs/`.
- Не создавай второй набор папок «для красоты»: структура — в `PROJECT_MAP.md`.
- `.meta` коммитится всегда. Не удаляй и не переименовывай вручную.

## Если появится AI-генерация 3D

- Разные генераторы смотрят в разные оси (условно: +X или −Z). Не угадывай: импортируй,
  измерь габарит и ориентацию, только потом собирай префаб.
- Текстуры от генераторов обычно sRGB; в линейном проекте их нельзя считать линейными.
- AI-реконструкция даёт **силуэт**, а не замысел: она не создаёт дизайнерские панели,
  швы и воротники. Не планируй на ней уникальный стиль без доводки руками/кодом.
- Не тащи в проект весь пайплайн генератора: только результат и `SOURCE.md`.

## Статус проверки

Проверено в FrostSpace:

- единицы и оси на FBX-roundtrip (`Tools/Blender/selftest.py`, Blender 5.2.2);
- `bake_space_transform=True` и совпадение габарита до/после импорта;
- компенсация масштаба на корне при обратном импорте (локальный меш в см,
  `scale = 0.01`, поворот 90° — мировой габарит при этом верный);
- существование типа `UniversalAdditionalCameraData` в URP-сборке (через `unity_reflect`);
- клипы роботов: `Idle`/`Walk`/`Sprint` нужной длины, in-place (EditMode-тесты, 2026-10-18);
- клипы животных: `Idle`/`Move` нужной длины, loop, без статичного провала в `Move`
  (EditMode `AnimalVisualPrefabTests`, 2026-10-19). После пересборки 2026-10-22 клипы несут
  root motion, а проверка «нет хода корневых кривых» его не видит: кость `Root` лежит под
  арматурой (`Armature/Root`), а тест пропускает пути с `/`. Итог 6/6 PASS — ход корня тестами
  больше не страхуется, его держит только `check_animal_clips.py`;
- импорт пересобранных 13 FBX в Unity (2026-10-22): ошибок импорта и предупреждений нет, ход
  `Root` за цикл `Move` совпадает с чекером Blender — Wolf 4.52, Cat 3.18, Dog 3.00, Cow 4.90,
  Horse/Zebra 4.94, Llama/Sheep 1.08, Pig/Pug 1.46, Spider 0.80 усл. ед. вперёд (+Z);
  у Eagle и Piranha (`fly`/`swim`) хода корня нет;
- габариты префабов животных совпадают с `target`/`metric` манифеста (тот же тест) и
  маршруты в Play Mode проходят все 13 актёров (2026-10-19);
- замер скорости стопы клипов в Blender и Unity: 0.93 / 8.92 против 0.91 / 8.92 м/с
  (2026-10-18);
- компенсация масштаба у FBX робота: локальный меш со `scale = 0.01` и поворотом 90°,
  мировой габарит верный (`probes/probe_fbx_import.py`);
- отражение статики по X от `bake_space_transform`: конвейер даёт
  `Unity(x,y,z) = (−x_bl, z_bl, −y_bl)`; лечится зеркалом X при экспорте (ADR 0007,
  2026-10-18);
- ориентация уровня после импорта: крыльцо −1.40, дверь −0.94, труба +1.42, фундамент
  +0.09 — совпадает с задуманным (2026-10-18);
- палитра `Level_*`: цвета из Unity-палитры, импорт с sRGB→linear
  (`LevelAssetPostprocessor`, 2026-10-18);
- палитра роботов переносится 1:1 (сравнено с палитрой): `R1_base` = `#385781`,
  `R3_panel` = `#39859C` после пересборки (2026-10-18).

Перенесено из проверок проекта-предшественника и **в FrostSpace не перепроверялось**:

- `ReadPixels` отдаёт линейные значения, PNG — sRGB;
- `material.mainTexture` в URP не читается, нужен `SetTexture("_BaseMap")`;
- камера, созданная кодом, не получает `UniversalAdditionalCameraData` автоматически;
- поведение Quaternius-материалов с `Alpha = 0` в превью Blender.

Эти пункты — рабочие правила, но при первом реальном использовании их нужно подтвердить
на конкретном ассете и записать результат.

## Звук прибытия (не Blender)

Звуки депо не импортируются из чужих пакетов: их генерирует
`Tools/Audio/build_sfx.py` (numpy + `wave`). Скрипт — единственный источник,
готовые WAV лежат в `Assets/_Project/Content/Audio/Arrival/` и пересобираются
одной командой:

```
python Tools/Audio/build_sfx.py --all
python Tools/Audio/build_sfx.py --check
```

| Клип | Роль | Петля |
|---|---|---|
| `wind_loop` | ветер депо | да |
| `rail_rumble_loop` | гул рельсов под едущим вагоном | да |
| `brakes` | тормоза перед остановкой | нет |
| `doors` | пневматика боковых створок | нет |
| `step_metal`, `step_snow` | шаги R13 по вагону и платформе | нет |
| `stop_thud` | удар остановки | нет |
| `cart_hum_loop` | гул грави-тележки | да |
| `title_drone_loop` | низкий гул чёрного титра | да |

Импорт настраивает `Assets/_Project/Editor/AudioArrivalImportPostprocessor.cs`:
моно 44.1 кГц; петли — Vorbis в памяти, короткие удары — PCM с предзагрузкой.
`--check` проверяет формат, пик, DC и бесшовность петель.

## Чек-лист перед «готово»

1. Модель в метрах, оси проверены.
2. Габарит после импорта совпадает с задуманным (числом, не на глаз).
3. Материал использует `_BaseMap`; цвет не пересвечен.
4. Flat shading сохранён, лишние материалы не созданы.
5. `.meta` на месте; пак лежит в `ThirdParty` с `SOURCE.md`.
6. В `Assets/` нет `.blend`, скриншотов и временных файлов.
