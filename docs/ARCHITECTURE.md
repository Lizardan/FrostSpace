# Архитектура FrostSpace

## Сейчас (факт)

Есть вертикальный срез на `Assets/Scenes/SnowLevel.unity` (build index 0):

- `FrostSpace.Features` (`Assets/_Project/Scripts/Features/`):
  `Locomotion/RobotLocomotion.cs` — движение через kinematic `CharacterController`,
  `Locomotion/LocomotionDiagnostics.cs` — стенд замера (`PROBE`) в Play Mode,
  `Camera/TopDownCamera.cs` — камера сверху-сзади.
- `FrostSpace.Editor` (`Assets/_Project/Editor/`): `RobotAssetPostprocessor` — импорт FBX
  (имена клипов, loop, sRGB). Меню-сборки уровня и префабов удалены намеренно (ADR 0005):
  контент не пересобирается скриптом.
- `FrostSpace.Tests.EditMode` (`Assets/_Project/Tests/EditMode/`) — проверки префабов и
  клипов.
- **Префаб — визуал, логика — на сценовом актёре.** `R*_Model.prefab` — варианты
  FBX-модели с `Animator` и `R*.controller`, без `CharacterController` и ввода.
  `Player` (тег, CC, `RobotLocomotion`) и `NPC_R*` (пустые узлы с визуальным ребёнком) —
  объекты сцены; причину фиксирует ADR 0004.
- Локомоция: клипы in-place, Root Motion выключен, `Animator.speed` = фактическая скорость
  / скорость клипа.
- `Assets/Scenes/Boot.unity` — неиспользуемая заготовка шаблона.

Ещё нет composition root, UI, сохранений, сети и ScriptableObject-конфигов; `Core/` и
`Infrastructure/` не созданы. Это **не** архитектурный долг: просто ещё не написано.

## Целевая минимальная основа (предложение)

Структура и пути — в `PROJECT_MAP.md`. Здесь — ответственность и зависимости.

| Слой | Путь | Ответственность |
|---|---|---|
| Core | `Assets/_Project/Scripts/Core/` | composition root, инициализация, контракты, загрузка сцен. Не знает про геймплей. |
| Features | `Assets/_Project/Scripts/Features/<Feature>/` | поведение и данные конкретной игровой функции. |
| Infrastructure | `Assets/_Project/Scripts/Infrastructure/` | интеграции с внешними системами, технические сервисы. |
| Editor | `Assets/_Project/Editor/` | только редакторные утилиты, `#if UNITY_EDITOR`. |
| Tests | `Assets/_Project/Tests/{EditMode,PlayMode}/` | EditMode и PlayMode тесты. |

Направление зависимостей:

```
Features ──→ Core
Infrastructure ──→ Core
Editor ──→ всё (только в редакторе)
Tests ──→ тестируемый слой
Core ──→ ничего из FrostSpace.*
```

Запрещено: `Core → Features`, `Features → Editor`, циклические зависимости между
фичами. Если двум фичам нужен общий контракт — он живёт в `Core`, а не в одной из них.

### Правила, которые не «на будущее», а следствие Unity

- **Композиция вместо поиска.** Ссылки передаются через `[SerializeField]`, конструктор
  или `Initialize` из composition root. `FindObjectOfType`/`GameObject.Find` в
  геймплейном коде запрещены (кроме `Awake` сцены/бутстрапа).
- **ScriptableObject — дизайн-данные**, не runtime-состояние. Ссылки на SO — в
  инспекторе, не через `Resources.Load`.
- **События** — когда они снижают связанность; не заменяют обычные вызовы автоматически.
- **Сцены.** Сейчас две: `SnowLevel` — игра, `Boot` — заготовка. Когда появится поток,
  раздели его на осмысленные сцены (bootstrap → menu → game), но не создавай пустые сцены
  заранее. Переходы — через один сервис загрузки, а не `SceneManager` по всему коду.
- **Сериализация.** Unity не сериализует интерфейсы, `Dictionary`, статику, делегаты,
  `readonly`. Для сложных данных — `[Serializable]`-класс/структура с полями.
- **asmdef** — это границы слоёв: `FrostSpace.Features` (runtime-фичи),
  `FrostSpace.Editor` (только редактор), `FrostSpace.Tests.*`. Не создавай сборку на
  каждую папку и не добавляй `autoReferenced`-хаки.
- **Производительность.** Не оптимизируй вслепую: профилируй. В горячих путях — без
  `GetComponent` каждый кадр, без лишних аллокаций, пулы для повторяющихся объектов.

### Чего сознательно нет

- DI-контейнера, event bus, service locator, ECS, MVVM, Clean Architecture «по учебнику».
- Сетевого слоя, сохранений, Addressables, UI-фреймворка — пока нет требований.
- Глобальных синглтонов: если появится необходимость, решение фиксируется ADR.

## Пробелы по приоритету

1. **Не зафиксирован продуктовый замысел.** Нельзя принимать архитектурные решения,
   которые зависят от жанра (сеть, сохранения, камера, масштаб мира).
2. **NPC без логики.** Акторы `NPC_*` статичны и играют Idle; `NpcController` — следующая
   фича, вешается на сценовый актёр, а не на префаб.
3. **Нет UI, сохранений, сети и конфигов.** Появятся вместе с требованиями; не создавай
   слои и сборки заранее.
4. **`Boot.unity` — заготовка** и лежит в `Assets/Scenes/`. Не перемещаем существующий
   ассет ради документации; новые сцены идут в тот же единственный корень.
5. **Unity MCP ссылается на `#main`.** В lockfile зафиксирован hash, но manifest плавает.
   Риск изменения имён инструментов; запинить позже отдельным решением.

## Как менять архитектуру

1. Сначала пойми существующую реализацию и её вызывающие места.
2. Опиши минимальный инкремент и критерии приёмки.
3. Если меняется контракт между слоями — сначала ADR, потом код.
4. Не представляй целевую схему как реализованную. В документах всегда разделяй
   «сейчас» и «предлагается».
